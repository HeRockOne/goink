> 日期：2026-07-31
> 分析对象：`internal/agent/phase_gate.go`、`internal/agent/agent.go` 门禁拦截逻辑、`门禁配置示例.md`
> 关联架构：ADR-0001（Prompt Caching 前缀稳定化）

---

## 一、门禁系统现状分析

### 1.1 门禁配置存储（已经做过缓存优化）

| 存储位置 | 是否占用 AI 上下文 | 说明 |
|---------|------------------|------|
| `app_config.phase_gate_config`（DB） | ❌ 不占 | `parsePhaseGateFromMessages` 优先读 DB（`agent.go:782`） |
| 系统消息内嵌 | ✅ 占（已弃用） | 回退方案，兼容旧版 skill 内嵌配置 |

**结论**：门禁配置本身**已经实现了"不进上下文"**——这是项目最早期的缓存优化之一。配置只由门禁代码读取，LLM 通过 `get_phase_gate_config` / `update_phase_gate_config` 工具按需访问，不占固定前缀。

### 1.2 门禁拦截机制（硬拦截，agent 层）

工具调用流程（`agent.go:443-477`）：
```
LLM 请求工具 → CheckToolAllowed(name) → 不通过则注入 <system-reminder> 拦截消息
                                        → 通过 → CheckEditPath(path) → 执行
```

- **阶段白名单**：每个 phase 的 `tools` 列表，非白名单工具被硬拦截
- **require**：切换阶段前必须成功调用的工具列表
- **set_phase** 始终放行，切换时校验 require + write 阶段字数
- 拦截结果通过 `<system-reminder>` 注入对话（appendMsg user 消息），引导 LLM 纠正

### 1.3 关键代码事实

1. **发送给 LLM 的 tools 数组始终是全量 57 个**（`agent.go:231` `registry.OpenAI(nil)`）
2. **`AllowedTools` 字段是死代码**：定义在 `llm/types.go:53`，但没有任何 provider 的 `buildPayload` 消费它，实际门禁靠 agent 层拦截
3. **门禁拦截消息会写入对话历史**（`appendMsg("user", <system-reminder>)`），成为动态部分

## 二、缓存优化的现状（ADR-0001 架构）

```
固定前缀（缓存命中，≈17,102 tokens）：
├─ L1 Identity（1,340）
├─ L2 Always skills（1,845）
├─ L3 Skill catalog（993）
└─ 工具定义 57 个（12,924）

动态部分（缓存失效区）：
├─ L4 NovelState（每轮刷新）
├─ user 消息 / assistant 消息 / tool 结果
└─ 门禁拦截注入的 <system-reminder> 消息
```

缓存策略的核心权衡（ADR-0001）：
- **为了前缀稳定，宁可全量发 57 个工具**，也不按阶段裁剪（裁剪会让 tools 数组每阶段变化，破坏缓存）
- 实测命中率 89-93%（`archive/billing-test-report.md`）

## 三、门禁能否进一步做缓存优化？—— 深度评估

### 3.1 门禁本身的配置：已优化到位（无需再动）

门禁配置存 DB、不进上下文、通过工具按需读取——**这是最理想的缓存友好形态**，没有优化空间。

### 3.2 真正的优化点：门禁与工具发送的矛盾

这是本次评估的**核心发现**。当前存在一个结构性矛盾：

| 事实 | 影响 |
|------|------|
| 每阶段白名单只有 17-23 个工具（示例配置，maintain 除外） | 大多数阶段只用到全量的 ~40% |
| 但发送给 LLM 的 tools 始终是全量 57 个 | 12,924 tokens 固定注入，其中 ~60% 在当阶段不可用 |
| 门禁在 agent 层硬拦截不可用工具 | LLM 实际看不到用不上的工具，但 payload 里仍带着 |

**矛盾本质**：按阶段裁剪 tools（省 token）↔ 全量发送（保缓存前缀）。ADR-0001 选择了后者。

### 3.3 可选的优化方案对比

#### 方案 A：维持现状（推荐基线）
- **逻辑**：全量发送，靠 agent 层白名单拦截
- **代价**：12,924 tokens 固定注入，但作为稳定前缀**每轮命中缓存**
- **缓存成本**：12,924 × 10% × 轮次 = 每轮 ~1,300 tokens 的缓存计费
- **优点**：前缀 100% 稳定，命中率 89-93% 已验证；门禁拦截逻辑简单
- **缺点**：token 基数大

#### 方案 B：按阶段动态裁剪 tools（已被 ADR-0001 否决）
- **逻辑**：`registry.OpenAI(allowed)` 只发当阶段工具
- **收益**：prepare 阶段可省 ~60%（12,924 → ~5,000 tokens）
- **致命问题**：阶段切换时 tools 数组变化 → **缓存前缀断裂** → 每次 set_phase 后缓存全失效
- **结论**：省了 token 但损失缓存，且门禁本来就在拦截，收益重叠。**不建议**。

#### 方案 C：阶段无关的"超集分组"（新思路，中风险）
- **逻辑**：不做按阶段裁剪，但把 57 个工具按"读/写/搜索/管理"分成 3-4 个**固定顺序的超集**，每个超集内部顺序稳定
- 例：`GET_TOOLS`（全部 get_* 只读工具）+ `WRITE_TOOLS`（create/update/delete）+ `UTILITY_TOOLS`（set_phase/run_subagent/...）
- **收益**：每个超集独立缓存。门禁拦截时只影响该超集内部，不破坏其他超集前缀
- **风险**：仍需全量发送，token 不省；复杂度增加，缓存收益边际
- **结论**：**不值得**。全量本身就是稳定前缀，分组不改变总大小。

#### 方案 D：llm 层真正消费 AllowedTools（低风险，纯收益）
- **逻辑**：把已经存在的死字段 `AllowedTools` 实现——在 `buildPayload` 里用 allowed 过滤 tools 数组
- **注意**：这会回到方案 B 的缓存问题，所以**不能**直接过滤。应只用于 OpenAI 兼容的 `tools` 字段做"可选裁剪开关"，默认关闭
- **结论**：可作为未来按阶段裁剪的开关预留，但默认应保持全量。

#### 方案 E：降低工具定义本身的大小 ⚠️ 已被否决（创作质量优先）
- 工具定义 12,924 tokens 里，description 和 schema 是主要体积
- 精简 description 表面上"双赢"（缓存更小、miss 更便宜）
- **但本项目是 AI 创作小说软件，质量第一。** 实际审查 `create_lore`/`create_timeline_entry` 等工具发现，description 里蕴含的是**完整创作方法论**，不是冗余：
  - `create_lore`：8 类世界观分类体系 + reveal_chapter_id 信息投放节奏 + is_public 悬念/反转设计
  - `create_timeline_entry`：importance 1-5 的伏笔回收节奏（小伏笔几章/中等一卷/核心贯穿全文）
  - 这些是**教会 AI 正确创作的核心指令**，精简 = 丢失创作能力
- **实际风险**（用户明确指出的质量红线）：
  1. AI 分不清工具（get_items/search_items、get_lore/search_lore 混淆）
  2. 参数漏填（schema 精简后 AI 不知道要填什么 → 设定录入不完整）
  3. 小说设定遗漏 → 后续章节衔接不上 → 偏离小说主旨
  4. 伏笔/反转/节奏设计丢失 → 长篇一致性崩塌
- **结论**：**坚决不做**。省 2-3K token 的收益远小于创作质量损失的风险。这正是"宁可不乱改，也不要影响写作质量"原则的体现。

## 四、综合结论

### 4.1 门禁系统本身 → 缓存优化已到位

门禁配置存 DB 不进上下文 + 硬拦截机制，已经是最优缓存形态。**没有新的缓存优化空间**。

### 4.2 门禁与缓存的矛盾 → 维持 ADR-0001 决策

| 维度 | 评估 |
|------|------|
| 按阶段裁剪 tools | ❌ 破坏缓存前缀，ADR-0001 已否决，维持 |
| 全量发送 + 门禁拦截 | ✅ 当前方案，前缀稳定，命中率 89-93%，维持 |
| 分组超集 | ❌ 复杂度增加，收益边际，不做 |
| 精简工具描述 | ❌ **坚决不做**。description 蕴含创作方法论（世界观分类/伏笔节奏/悬念设计），精简=丢失创作能力，违背质量第一原则 |
| AllowedTools 死代码 | ⚠️ 可清理或实现为可选开关，非阻塞 |

### 4.3 给后续 AI 的关键提示

1. **不要因为"门禁白名单只有 20 个工具"就尝试按阶段裁剪 tools**——这会破坏缓存前缀，与 ADR-0001 冲突
2. 门禁拦截是 agent 层行为，`AllowedTools` 字段目前未在 llm 层消费，**不要误以为它已经在裁剪 tools**
3. **不要精简工具 description/schema**——它们是创作方法论的载体（世界观分类体系、伏笔回收节奏、悬念反转设计），不是 token 冗余。本项目是创作软件，**创作质量永远优先于 token 节省**
