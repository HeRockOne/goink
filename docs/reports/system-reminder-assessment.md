# `<system-reminder>` 注入机制评估报告：能否用 Go 代码替代、不走上下文？

> 日期：2026-07-31
> 目的：用户提出——`<system-reminder>` 注入消息是否有必要发给 AI？能否像门禁配置一样走 Go 代码、不进上下文？
> 前置原则：创作质量第一。任何替代方案不得损害创作能力。

## 二、结论先行

**`<system-reminder>` 的 5 类用途中，4 类必须保留，1 类（门禁相关）也建议维持现状——最终结论是：不做替代，全部保留。**

用户提的"像门禁配置一样走 Go"思路很有价值，但深入分析后结论是：**门禁配置能走 Go 是因为它是静态规则（writing-kernel 已在开头告知），而 reminder 大多是动态纠偏/反馈信号（AI 做错事时的即时引导），性质不同，不可替代。**

**重要修正**：本报告初版曾建议"失败禁用改硬拦截、拦截去重"——经用户指出门禁设计理念后确认**这些是危险的**：
- 失败禁用硬拦截会卡死 require 链路（被禁工具若是 require 工具，阶段永远无法推进）
- 拦截去重会削弱 AI 行为纠正能力
- 这些方案违背门禁"防遗漏工作的强制链路"理念

## 三、逐类评估可行性、风险、安全边界

### 3.1 硬拦截结果（门禁拦截 / 路径拦截 / set_phase 结果）

**现状**：Go 已经强制执行拦截——工具**根本没执行**，返回了 error。reminder 告诉 AI "当前阶段 [write] 不允许使用 [create_lore]，请调用 set_phase 切换"。

**关键事实（修正）**：
- **AI 本来就清楚每个阶段要做什么**：`writing-kernel.md`（always 模式，会话开头全量注入）明确列出每阶段 required 工具（prepare 9 项 / outline edit / write edit / review run_subagent / maintain 15 项清单）——这是门禁设计理念的"告知层"。
- 身份提示词（identity.go:171-177）也给出 5 阶段完成条件表。
- 拦截 error（agent.go:459）提供具体阶段名。

**所以门禁拦截 reminder 的作用不是"告诉 AI 有哪些工具"，而是"纠正 AI 当前错误行为 + 引导下一步"**（"请调用 set_phase 切换到正确阶段"）。这属于**行为引导**，不是冗余信息。

**能否替代？** 
- 门禁配置本身（tools/require 白名单）**不需要每轮注入**——已由 writing-kernel 告知，AI 主动查 get_phase_gate_config 是补充。
- 但拦截时的 reminder 是**实时纠正信号**，不可移除（AI 在错误阶段调错工具时，需要明确指引而不是冷冰冰的 error）。

**评估**：
| 维度 | 评估 |
|------|------|
| 可行性 | ⚠️ 部分——配置无需常驻已实现；但拦截 reminder 是行为纠正，保留 |
| 风险 | 拦截 reminder 移除会降低"引导纠正"能力，AI 可能反复试错 |
| 安全边界 | 保留 set_phase 成功/失败状态注入；保留拦截引导语 |
| token 影响 | 门禁配置已不占常驻（writing-kernel 常驻是设计），拦截 reminder 很小 |

**建议**：门禁相关 reminder **维持现状**。它服务于"门禁链路稳定推进"理念——每次拦截都是对 AI 的即时纠偏，价值远大于 token 成本。

### 3.2 软约束提醒（失败3次禁用 / 死循环 / 催推进）

**现状**：
- 失败3次禁用：`failCnt` 内存计数 + 注入 reminder，Go 未硬拦（agent.go:552）
- 死循环：`isStuckLoop` 注入提醒，Go 未硬停（agent.go:657）
- 催推进：require 满足后注入 reminder（agent.go:677）

**能否替代？需要重新评估（重要修正）**：

**失败3次禁用 → 不能简单改 Go 硬拦截。**
- `failCnt` 只统计 `ErrKind == "system"`（系统故障），**不统计用户错误/门禁拦截**——它是"防系统故障循环"，不是"防 AI 乱来"
- **致命风险**：若被禁工具是门禁 require 工具（如 get_writing_context），硬禁用后 AI 永远无法满足 require → **阶段卡死 → 门禁链路中断**。这**直接违背门禁设计理念**（门禁是保证 AI 稳定走完链路，不是卡死它）
- 当前软提醒方案反而安全：AI 收到提醒后换策略重试，`failCnt` 成功即清零（agent.go:550），不锁死

**死循环检测 → 已有保护，无需硬停**：`isStuckLoop` 只是注入提醒让 AI 自行收敛，配合 MaxTurns 兜底（50/100 轮）。改成硬停反而可能误杀正常长轮次创作（AI 可能要 20 轮才完成一章的 maintain）。

**催推进 → 维持提醒**：门禁设计"不自动推进"（phase_gate.go:18）是**刻意**的——让 AI 自己判断阶段完成并主动 set_phase，这是创作流程的"自觉性"要求，不是省 token 点。自动推进会破坏"AI 主动维护状态"的心智模型。

**评估**：
| 维度 | 评估 |
|------|------|
| 可行性 | ⚠️ 三个都不适合硬约束化 |
| 风险 | 硬禁用会卡死 require 链路；硬停会误杀长轮次；自动推进破坏设计理念 |
| 结论 | **维持现状。** 这些软提醒服务于"门禁链路稳定推进 + AI 自觉维护"的理念，改硬约束是**倒退** |

### 3.3 压缩状态（摘要 + 提醒）——必须保留

**现状**：压缩后注入 `<system-reminder>上下文已压缩，按摘要继续` + 摘要本身（compress.go:256,260）。

**不能替代**：AI **必须知道**自己被压缩了，否则它会困惑"为什么中间缺了一大段"。摘要内容是压缩后的唯一记忆，Go 无法生成它（需要 LLM 理解）。

**评估**：❌ 不可替代，保持现状。

### 3.4 用户/人工反馈（slash / 审批）——必须保留

**现状**：用户 `/` 触发技能（slash_command.go）、人工审批意见（rw_tools.go:225）。

**不能替代**：这是**人的意图**，必须进入上下文让 AI 理解。Go 无法替用户表达。

**评估**：❌ 不可替代，保持现状。

### 3.5 工具创作指令（全量替换后的维护清单）——必须保留

**现状**：rw_tools.go:229-232——章节全量替换后注入"请执行角色设定/时间线/读者认知/弧线节点 4 项维护"。

**不能替代**：这是**创作方法论指令**，告诉 AI 写完章后必须维护哪些维度。属于"代码级质量门"的一部分，删掉会导致维护遗漏。

**评估**：❌ 不可替代，保持现状。

| ❌ | 压缩摘要/用户反馈/创作指令 用 Go 替代 | — | 🔴 丢创作记忆/丢人意图/丢维护指令 | — | 高危，**不做** |

## 五、核心原则

1. **门禁系统是"防 AI 遗漏工作的强制链路"**，设计理念是：让 AI 始终遵循 prepare→outline→write→review→maintain 稳定推进，防止它忘了维护设定、漏填设定、虚报过程、不读 skill 直接写、埋头不听指挥。**任何优化不得破坏这个链路**。
2. **门禁的告知层在 writing-kernel（always skill）**——每阶段 required 工具已在会话开头全量注入，AI 不需要每轮查 get_phase_gate_config。
3. **门禁的校验层在 Go**——require 只统计成功调用（phase_gate.go:175）、失败不算、硬拦截不可用工具、write 转出强制字数。这是"防虚报过程"的硬保障。
4. **门禁的纠偏层在 reminder**——拦截时的引导语是"AI 做错事时的即时纠正"，不是冗余，价值远超 token 成本。
5. **软提醒不能简单升级为硬约束**：
   - 失败禁用硬拦截 → 被禁工具若是 require 工具，阶段卡死，违背链路理念
   - 死循环硬停 → 误杀正常长轮次（一章 maintain 可能 20 轮）
   - 自动推进 → 破坏"AI 主动维护状态"的心智模型
6. **token 优化正确方向**：不在这层省。门禁配置已不占常驻（writing-kernel 告知），reminder 是必要的实时反馈。若真需省 token，应回到 P1 报告（压缩窗口/摘要锚定），那些才是质量安全的方向。

## 六、安全边界清单

| 约束 | 说明 |
|------|------|
| 门禁链路完整性 | 任何改动不得让 require 工具被永久禁用、不得自动跳过阶段、不得绕过硬校验 |
| 创作自觉性 | set_phase 保持"AI 主动调用"，不自动推进 |
| 纠偏引导 | 拦截 reminder 保留，它是 AI 行为纠正的即时信号 |
| 失败禁用 | 保持软提醒（failCnt 成功清零），不硬禁工具 |
| 创作指令/摘要/用户反馈 | 无论 token 多少，永不移除 |
