# `<system-reminder>` 注入机制评估报告：能否用 Go 代码替代、不走上下文？

> 日期：2026-07-31
> 目的：用户提出——`<system-reminder>` 注入消息是否有必要发给 AI？能否像门禁配置一样走 Go 代码、不进上下文？
> 前置原则：创作质量第一。任何替代方案不得损害创作能力。

---

## 一、`<system-reminder>` 全景盘点（共 5 大类，用途完全不同）

逐一梳理代码中所有注入点（`internal/agent/agent.go`、`compress.go`、`app/slash_command.go`、`internal/mcp_tools/`）：

| # | 类别 | 注入点 | 内容 | 是否可由 Go 替代 |
|---|------|--------|------|----------------|
| 1 | **硬拦截结果** | agent.go:425,433,449,467 | set_phase 成功/失败、门禁拦截工具、edit 路径拦截 | ⚠️ 见 §3.1 |
| 2 | **软约束提醒** | agent.go:553（失败3次禁用）、:657（死循环）、:677（require满足催推进） | 让 AI 主动遵守的提醒 | ⚠️ 见 §3.2 |
| 3 | **压缩状态** | compress.go:38,166,256,260 | "上下文已压缩，按摘要继续" + 摘要 | ❌ 必须给 |
| 4 | **用户/人工反馈** | slash_command.go:46,49,52；rw_tools.go:225（审批反馈） | 用户 `/` 指令、人工审批意见 | ❌ 必须给（人意图） |
| 5 | **工具创作指令** | rw_tools.go:229-232（全量替换后维护清单）、delete_tools.go:124 | 触发后的创作方法论指引 | ❌ 必须给（创作规则） |

---

## 二、结论先行

**不能一刀切。5 类里只有 2 类（硬拦截结果 + 部分软约束）可以部分优化，另外 3 类（压缩/用户反馈/创作指令）必须保留进上下文。**

用户提的"像门禁配置一样走 Go"思路**部分可行**，但必须谨慎——因为门禁配置是**静态规则**（Go 读取后自己判断），而 `<system-reminder>` 大多是**动态事件**（需要 AI 知道"刚才发生了什么"才能正确决策）。两者性质不同。

---

## 三、逐类评估可行性、风险、安全边界

### 3.1 硬拦截结果（门禁拦截 / 路径拦截 / set_phase 结果）

**现状**：Go 已经强制执行拦截——工具**根本没执行**，返回了 error。reminder 只是**告诉 AI 为什么被拦**（"当前阶段 [write] 不允许使用 [create_lore]"）。

**能否替代？** 不能完全替代，但**可以大幅精简**。

**理由**：
- 门禁配置（tools 白名单）存 DB，Go 拦截，AI **本来就知道**哪些工具可用（每个阶段的白名单在 get_phase_gate_config 可查，且身份提示词里有门禁表）
- 被拦截时 AI 收到的工具结果是 `{success:false, error:"门禁拦截..."}`（agent.go:459）——**这个 error 已经在上下文里了**
- reminder 和 tool error **重复**了同一信息！

**评估**：
| 维度 | 评估 |
|------|------|
| 可行性 | ✅ 可移除大部分冗余 reminder，tool error 已传达信息 |
| 风险 | 🟡 中低——reminder 措辞（"请调用 set_phase 切换到正确阶段"）比裸 error 更"指导性"，移除后 AI 可能不知所措 |
| 安全边界 | 必须**保留** set_phase 成功后的状态 JSON（AI 需要知道当前阶段）；失败场景可精简 |
| token 影响 | 每次拦截省 ~50-100 tokens（注入消息），长期看拦截频繁时明显 |

**建议**：将"拦截工具"的 reminder 精简为复用 tool error（不重复注入），保留 set_phase 成功状态。**属于低风险改进，但不紧急。**

### 3.2 软约束提醒（失败3次禁用 / 死循环 / 催推进）

**现状**：
- 失败3次禁用：`failCnt` 只在内存计数 + 注入 reminder，**Go 没有硬拦截**（agent.go:552）
- 死循环：`isStuckLoop` 检测到后注入提醒，**Go 没有硬停**（agent.go:657）
- 催推进：require 满足后注入 reminder，**Go 没有硬拦**（agent.go:677）

**能否替代？** **可以，而且应该——用 Go 硬约束替代软提醒。**

**理由**（这才是真正的"像门禁配置一样"思路）：
| 软提醒 | Go 硬约束替代 | 效果 |
|--------|--------------|------|
| "工具失败3次被禁用" | `failCnt==3` 时把该工具**加入禁用集合**，后续调用直接拦截不执行 | 更可靠（AI 可能忽略 reminder） |
| "可能陷入重复调用" | `isStuckLoop` 时**强制终止本轮**，返回当前成果 | 更可靠 |
| "require 已满足必须 set_phase" | **Go 自动推进**阶段（当前刻意不自动，靠提醒） | 更可靠 |

**评估**：
| 维度 | 评估 |
|------|------|
| 可行性 | ✅ 高——这是纯 Go 逻辑，不涉及创作判断 |
| 风险 | 🟢 低——硬约束比软提醒更可靠；但死循环"强制终止"需小心别误杀正常长轮次 |
| 安全边界 | 禁用集合要本轮内有效（跨轮重置）；死循环终止前先保存已产出内容 |
| token 影响 | 每次省 ~50-80 tokens，且**行为更可靠** |

**建议**：这是最值得做的。**把"失败3次禁用"从提醒改为 Go 硬拦截**（简单、纯收益、质量更稳）。死循环和催推进次之。

### 3.3 压缩状态（摘要 + 提醒）——必须保留

**现状**：压缩后注入 `<system-reminder>上下文已压缩，按摘要继续` + 摘要本身（compress.go:256,260）。

**不能替代**：AI **必须知道**自己被压缩了，否则它会困惑"为什么中间缺了一大段"。摘要内容是压缩后的唯一记忆，Go 无法生成它（需要 LLM 理解）。

**评估**：❌ 不可替代，保持现状。

### 3.4 用户/人工反馈（slash / 审批）——必须保留

**现状**：用户 `/` 触发技能（slash_command.go）、人工审批意见（rw_tools.go:225）。

**不能替代**：这是**人的意图**，必须进入上下文让 AI 理解。Go 无法替用户表达。

**评估**：❌ 不可替代，保持现状。

### 3.5 工具创作指令（全量替换后的维护清单）——必须保留

**现状**：rw_tools.go:229-232——章节全量替换后注入"请执行角色设定/时间线/读者认知/弧线节点 4 项维护"。

**不能替代**：这是**创作方法论指令**，告诉 AI 写完章后必须维护哪些维度。属于"代码级质量门"的一部分，删掉会导致维护遗漏。

**评估**：❌ 不可替代，保持现状。

## 四、综合建议（按收益/风险排序）

| 优先级 | 动作 | 类型 | 质量影响 | token 影响 | 风险 |
|--------|------|------|---------|-----------|------|
| **P1** | 失败3次禁用改为 **Go 硬拦截**（加禁用集合，替代 reminder） | 软约束→硬约束 | ✅ 更可靠（AI 忽略提醒也能拦住） | 省少量 | 低 |
| **P2** | 门禁拦截 reminder 与 tool error 去重（拦截场景不重复注入） | 冗余消除 | 无（信息已在 error） | 省 ~50-100/次 | 中低 |
| **P3** | 死循环"强制终止"硬约束（先保存产出再终止） | 软约束→硬约束 | ✅ 更可靠 | 省少量 | 中 |
| **P4** | require 满足自动推进阶段 | 架构变更 | ⚠️ 改变创作流程交互（用户可能想人工控制） | 省 | 中高 |
| ❌ | 压缩摘要/用户反馈/创作指令 用 Go 替代 | — | 🔴 丢创作记忆/丢人意图/丢维护指令 | — | 高危，**不做** |

---

## 五、核心原则

1. **Go 代码适合替代"确定性规则"**：失败计数、死循环判定、阶段推进——这些是逻辑判断，Go 比 reminder 更可靠。
2. **Go 代码不适合替代"信息传达"**：压缩摘要（AI 需要记忆）、用户意图（人的输入）、创作方法论（质量指令）——这些必须进上下文。
3. **门禁配置走 Go 是特例**：因为白名单是**静态规则**，Go 读 DB 自己判断即可，AI 不需要每轮看到它。而 `<system-reminder>` 大多是**动态事件反馈**，性质不同。
4. **正确方向**：与其"移除 reminder 省 token"，不如**把软提醒升级为硬约束**——既更可靠（质量提升）又顺带省 token（不违背质量第一，反而是质量优先）。

## 六、安全边界清单

| 约束 | 说明 |
|------|------|
| 禁用集合作用域 | 本轮 turn 内有效，跨轮重置（避免一次异常永久禁工具） |
| 死循环终止前置 | 先 flush 已产出的 content/tool 结果，再终止（不丢工作） |
| 自动推进开关 | 若实施 P4，必须保留手动模式（用户可关），不强制 |
| 拦截去重 | 只去重"拦截失败"场景；set_phase 成功状态仍注入 |
| 创作指令/摘要/用户反馈 | 无论 token 多少，永不移除 |
