## 一、项目背景

### 1.1 起因

用户（非程序员）管理一个 AI 自动写作系统 Goink，希望优化 token 消耗以降低成本。全程由 AI 辅助分析和实施。

### 1.2 核心约束

- **质量第一**：保证 AI 能听懂指令，不降低写作质量
- **保守实施**：宁可不动，也不要冒质量风险
- **完整记录**：记录所有讨论和决策，防止遗忘

## 二、分析过程

### 2.1 第一轮分析（错误假设）

**假设**：工具 Schema 是最大开销（~10,500 token/轮）

**基于**：
- 52 个工具 × ~200 token/工具 = 10,500 token
- 行业调研显示工具定义占 55K-134K token

**结论**：优化工具 Schema 可以节省大量 token

### 2.2 第二轮分析（发现错误）

**发现**：实际系统上下文只有 5K（不是 17K）

**基于**：用户提供的基线测试数据
```
总占用：52K / 1.0M（5%）
系统上下文：5K（0.4%）
用户输入：1K（0.1%）
AI 输出：22K（2.1%）
工具结果：25K（2.3%）
```

**关键修正**：
- 工具定义实际只有 ~1K（不是 10K）
- 门禁配置已经在做分阶段裁剪（每阶段 20-52 个工具）
- 52K 是整个单章流程的总消耗（不是单轮）

### 2.3 第三轮分析（最终理解）

**理解**：
1. 门禁配置已经在做分阶段裁剪
2. writing_context 已经在做数据聚合
3. 52K/章 的消耗已经很高效
4. 优化空间比预估的小很多

## 五、实施方案

### 5.1 Prompt Caching（✅ 已实施）

**实施时间**：2026-07-28

**改动文件**：
- `app/chat.go` — writeSystemMessages 函数
- `app/chat.go` — chatImpl 函数

**关键改动**：
1. `writeSystemMessages` 只写入稳定前缀（identity + always + catalog），不写 novelState
2. `chatImpl` 在加载消息后动态注入 novelState（在系统消息之后、用户消息之前）

**效果**：
- 前缀（identity + always + catalog）稳定，DeepSeek 会缓存
- novelState 移到动态部分，不破坏缓存

**验证状态**：构建成功，待测试

### 5.2 Token-Efficient Tool Use（待评估）

**原理**：
- Anthropic Claude 4+ 内置功能
- 压缩工具调用结果的序列化格式
- 减少输出 token 消耗（平均 14%，最高 70%）

**当前状态**：Goink 主要使用 DeepSeek/OpenAI 兼容格式，此方案可能不适用。需要评估是否使用 Anthropic 模型。

**预计效果**（如果适用）：
```
输出 token：22K → ~15K（节省 32%）
单章节省：~7K
```
